# 2026-07-31 Incident: "DAG never calls providers"

A session-long incident where the DAG appeared healthy but failed to reach
providers, followed by request-shape 400s, and finally by a noisy health
watcher. Everything below was diagnosed and fixed the same day.

## Root causes

1. **Keys not in the TUI process environment** — a long-lived parent shell
   predated the keys, so the TUI never had them; subagents silently degraded to
   session-JWT auth → 401s. Fixed operationally by restarting the TUI from a
   shell that sourced the login profile (which exports the three keys).
2. **Pre-fix API request shapes** — missing static `anthropic-version` header
   (silently dropped when placed inside `env_http_headers`) and OpenAI models
   routed to `/v1/chat/completions` instead of `/v1/responses` (causing the
   "Function tools with reasoning_effort" 400). Fixed in `config.toml`
   (see `fixes.md`).
3. **Watcher defects** — an unbound-variable crash on one code path and a
   dedupe bug producing a 2-minute nag loop. Fixed (see `fixes.md`).

## Outcome

- All three keys present in the TUI env, matching `credentials.toml`, and
  live-authenticating (HTTP 200) against their providers.
- All seven roles / five model slots proven working end-to-end.
- Watcher healthy on a 60-second cadence with the new persistent-alert
  behavior.
